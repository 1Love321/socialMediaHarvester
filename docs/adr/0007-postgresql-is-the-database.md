# PostgreSQL is the database

All harvester data lives in one PostgreSQL database. Brand, Handle, Post, Authorization and Collection Run are ordinary tables with foreign keys. Raw Payloads are a `jsonb` column (ADR 0006). Metric Snapshots and Handle Snapshots are append-only tables with a unique key on (Post or Handle, Collection Run, Public/Private label), so a retried Collection Run can't write the same snapshot twice.

We chose this over MongoDB even though the APIs return JSON and snapshots are time series. A prototype with real YouTube data and one year at the reference load (~30M Metric Snapshots, 500 Handles) showed that every UI query is fast enough on both databases. PostgreSQL was faster for the Brand/Handle/Post queries and enforces the one-snapshot-per-run rule; MongoDB time series collections can't have unique indexes or transactional writes. MongoDB was faster at the per-Handle daily aggregate (6 ms vs 46 ms), loaded faster, and used ~1.7 GB instead of ~12 GB. We accept that size: Raw Payloads (~1.8 KB each) fall under PostgreSQL's ~2 KB compression threshold and are stored uncompressed. The JSON is only at the edge (write once, read by the Normalizer, deleted after 30 days); the data we query and analyse is a relational hierarchy.

If snapshot volume grows by an order of magnitude or aggregate charts get slow, add TimescaleDB to the same database (same schema; note its licence if we ever host it for customers) before considering another database. See [the decision](https://github.com/rahmed12/socialMediaHarvester/issues/8) and the prototype on branch `prototype/database-choice`.
