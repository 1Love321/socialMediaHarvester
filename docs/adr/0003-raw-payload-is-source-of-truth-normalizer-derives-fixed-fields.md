# Raw Payload is the source of truth; a Normalizer derives fixed fields from it

Every fetch stores the Platform's Raw Payload first, and a Normalizer then derives the Post and the Metric Snapshot from it. It uses per-Platform YAML field mappings plus a small per-Platform code hook for derived fields. The Normalizer runs inline, Post by Post, during each Collection Run, and can be re-run over whatever Raw Payloads remain, e.g. after a new fixed field is added or a mapping is fixed. Posts and Metric Snapshots use a small set of typed fixed fields, with no catch-all set of extra metrics. A metric outside that set lives only in the Raw Payload until a field and mapping are added. The frontend reads only normalized records, never Raw Payloads.

We rejected storing only normalized data, because Platform field names and metric meanings keep changing and anything not mapped on day one would be lost. We also rejected an open set of metric names and values on each snapshot, because the users only need a known set of fields and typed columns chart and sum cleanly. The cost is extra storage for a Raw Payload per fetch. Also, a pruned Raw Payload can no longer be re-normalized, which constrains how Raw Payload history is retained (see ADR 0006). See [the decision](https://github.com/rahmed12/socialMediaHarvester/issues/9).
