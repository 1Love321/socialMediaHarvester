# One Harvester and one Platform Login per Platform, plugged in through a one-method interface

Each Platform plugs in as its own package: a Harvester implementing a single-method interface (it pages and batches however its API requires, returns a Harvest and never saves anything), plus a Handle lookup, its Normalizer mapping, its config (on/off switch, credentials, quota limits, retention) and its own Platform Login. The core finds Platforms by string key, never imports a Platform package (enforced by a test), and owns the quota counter that Harvesters charge against. Shared behaviour such as HTTP calls, retries, paging and the Meta login sits in helpers passed in to each Harvester, not in an abstract base class.

We rejected an abstract base class with fixed steps because the APIs don't share a sequence: YouTube lists and then batch-fetches stats, Instagram returns Posts and counts in one newest-first read, and Facebook reads two edges. We also rejected one login per company (one "Connect with Meta" for both Facebook and Instagram) in favour of one Platform Login per Platform, because one button per Platform is easier to follow. The cost is that an owner of a linked Facebook Page and Instagram account goes through Meta's login twice, and revoking on Meta's side ends both Authorizations at once. See [the decision](https://github.com/rahmed12/socialMediaHarvester/issues/10).
